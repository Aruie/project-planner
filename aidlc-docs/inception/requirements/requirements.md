# 개발 산출물 관리 플랫폼 요구사항정의서

## 1. 문서 정보
- **문서명**: 개발 산출물 관리 플랫폼 요구사항정의서
- **문서 ID**: REQ-AIDLC-001
- **상태**: Draft — Requirements Analysis 완료, 사용자 승인 대기
- **작성일**: 2026-09-02
- **작성자**: 관리자(임시 자동 로그인 사용자)
- **요구사항 분석 깊이**: Comprehensive

## 2. 의도 분석
- **사용자 요청**: 개발 산출물을 Markdown 중심으로 관리하고, 정형 Excel 산출물 생성, 작업 초안과 확정 버전 스냅샷, 버전 간 diff, 이미지/표, RFP 기반 요구사항정의서 AI 초안 생성을 제공하는 웹 애플리케이션 구축.
- **요청 유형**: 신규 프로젝트
- **범위 추정**: 다중 컴포넌트 시스템(React UI, FastAPI API, DynamoDB, S3, Bedrock 및 문서 생성 모듈)
- **복잡도 추정**: Complex
- **성공 기준**: 사용자가 프로젝트 안에서 산출물을 생성·편집하고, 하나의 작업 초안을 버전으로 확정하며, 버전 간 변경사항을 명확하게 보고, 정형 문서/Excel을 생성하고, RFP 텍스트로 요구사항정의서 초안을 만들 수 있다.

## 3. 제품 목표 및 범위
### 3.1 제품 목표
1. 개발 산출물의 원본을 구조화된 Markdown 중심 모델로 일관되게 보관한다.
2. 정형 산출물은 고정 Excel 양식으로 생성하고, 그 밖의 산출물은 범용 Markdown 양식으로 관리한다.
3. Git을 사용자에게 노출하거나 내부 백엔드로 사용하지 않고, DynamoDB 스냅샷 기반 버전 관리와 diff를 제공한다.
4. 작성 중인 초안과 확정 버전을 분리해, 확정 시점과 변경 내용을 명확히 추적한다.
5. RFP 등 텍스트 입력으로 Amazon Bedrock이 요구사항정의서 초안을 생성하도록 한다.

### 3.2 MVP 포함 범위
- 산출물 슈퍼클래스 개념과 Markdown/Excel 하위 유형
- 프로젝트, 문서, 버전의 3계층 관리
- 범용 Markdown 문서와 정형 Excel 문서 4종
- 표 및 이미지 첨부
- 단일 Draft, 확정 스냅샷, 변경내역, diff
- Markdown/DOCX 및 Excel(XLSX) 생성
- RFP 텍스트 기반 요구사항정의서 AI 초안 생성
- 임시 관리자 자동 로그인

### 3.3 제외 범위
- PowerPoint(PPT/PPTX) 산출물
- RFP의 PDF/DOCX 파일 업로드·파싱 및 기존 산출물 자동 참조 입력
- 다중 사용자 인증/권한 모델의 완성 구현
- 인프라 배포 자동화 및 프로덕션 운영 설계
- 실제 Git 저장소를 이용한 버전 관리

## 5. 도메인 모델
### 5.1 계층
- **프로젝트**: 여러 개발 산출물을 묶는 최상위 컨테이너.
- **문서(산출물)**: 프로젝트에 속하며 한 가지 산출물 유형을 갖는다.
- **Draft**: 문서마다 정확히 하나 존재하는 현재 작업본. 사용자가 편집하는 대상이다.
- **확정 버전**: Draft를 버전 생성으로 확정한 불변 전체 스냅샷. 버전 번호, 생성 시각, 작성자, 변경 요약을 포함한다.

### 5.2 산출물 유형
- **MarkdownDocument**: 범용 문서 유형. 대부분의 비정형 개발 산출물을 하나의 Markdown 템플릿으로 관리한다.
- **ExcelDocument**: 다음의 고정 양식 하위 유형을 갖는다.
  - 요구사항정의서
  - 추적표(사용자스토리 ↔ 요구사항 ↔ 테스트케이스)
  - 테스트 시나리오 및 결과서
  - 범용 Excel
- **향후 확장**: PPT/PPTX 산출물은 후속 릴리스에서 추가한다.

### 5.3 원본 및 표현 규칙
- 모든 산출물은 타입, 공통 메타데이터, 본문 콘텐츠를 가진 정규화된 Markdown 중심 문서 모델을 원본으로 사용한다.
- MarkdownDocument는 원본 Markdown을 편집·렌더링·저장한다.
- ExcelDocument는 같은 문서 모델의 구조화된 데이터를 고정 Excel 양식으로 생성한다.
- 외부 공유용 문서는 필요 시 Markdown→DOCX 또는 문서 모델→XLSX로 생성한다. 생성본은 원본 및 확정 버전을 대체하지 않는다.

## 6. 기능 요구사항
### FR-001 프로젝트 관리
시스템은 프로젝트를 생성, 조회, 수정하고 프로젝트별로 문서를 분리해 관리해야 한다.

**수용 기준**
- 프로젝트별 문서 목록과 각 문서의 유형·최신 확정 버전·Draft 수정 상태를 볼 수 있다.
- 문서는 정확히 하나의 프로젝트에 속한다.

### FR-002 산출물 생성 및 유형 관리
시스템은 사용자가 MarkdownDocument 또는 ExcelDocument 및 그 하위 유형을 선택해 문서를 생성하게 해야 한다.

**수용 기준**
- ExcelDocument 생성 시 요구사항정의서, 추적표, 테스트 시나리오/결과서, 범용 Excel 중 하나를 선택할 수 있다.
- MarkdownDocument 생성 시 범용 Markdown 템플릿과 표지/변경내역을 위한 front matter 기본값을 제공한다.

### FR-003 공통 메타데이터
시스템은 모든 문서 및 확정 버전에 문서 제목, 문서 ID, 버전, 작성일, 작성자를 저장해야 한다.

**수용 기준**
- 작성자는 버전 저장을 누른 사용자로 기록한다.
- MVP에서는 임시 관리자 자동 로그인 사용자를 작성자로 자동 기록한다.
- Markdown 원본은 YAML front matter로 공통 메타데이터를 표현할 수 있다.

### FR-004 Markdown 작성 및 렌더링
시스템은 MarkdownDocument 본문 작성, 표 작성, 미리보기 및 저장을 제공해야 한다.

**수용 기준**
- 표준 Markdown과 GFM 스타일 표를 지원한다.
- 표지 및 변경내역 표시는 front matter와 버전 이력으로 자동 구성한다.
- 사용자가 본문을 수정해도 확정 버전은 변경되지 않는다.

### FR-005 이미지 첨부
시스템은 문서에 이미지를 첨부하고 Markdown 본문 또는 Excel 출력에 참조할 수 있어야 한다.

**수용 기준**
- 이미지 원본은 S3에 저장하고, DynamoDB에는 S3 객체 키/참조 정보만 보관한다.
- 이미지 참조는 해당 문서 및 버전과 연관된다.
- 이미지가 누락되거나 접근 불가하면 문서 원본은 보존하고 렌더링/생성 시 오류를 사용자에게 알린다.

### FR-006 고정 Excel 양식 생성
시스템은 ExcelDocument 유형별 고정 양식을 openpyxl로 생성해야 한다.

**수용 기준**
- 모든 Excel 출력은 첫 번째 시트에 표지, 두 번째 시트에 변경내역을 둔다.
- 이후 시트는 선택한 산출물 유형의 본문 데이터 및 고정 열 구조를 사용한다.
- 요구사항정의서, 추적표, 테스트 시나리오/결과서, 범용 Excel 각각에 별도 템플릿 정의가 존재한다.
- Excel 문서에 표와 첨부 이미지를 포함할 수 있다.

### FR-007 작업 초안 관리
시스템은 문서당 하나의 현재 Draft를 유지해야 한다.

**수용 기준**
- 편집은 Draft에만 반영된다.
- 새 문서 생성 시 최초 Draft가 생성된다.
- 버전 확정 뒤 새 Draft는 확정된 내용의 복사본으로 계속 편집할 수 있다.

### FR-008 버전 확정 및 변경내역
시스템은 사용자가 Draft를 확정 버전으로 저장하게 해야 한다.

**수용 기준**
- 확정 전 시스템은 생성될 버전 번호, 작성자, 생성 일시 및 자동 산출한 변경 요약을 사용자에게 보여주고 확인을 받아야 한다.
- 확인 후 전체 Draft(메타데이터, 본문/구조화 데이터, 이미지 참조)를 immutable 스냅샷으로 저장한다.
- 변경내역에는 버전번호, 일시, 작성자, 변경 요약을 자동 추가한다.
- 실패한 확정 요청은 부분 버전을 남기지 않아야 하며 기존 Draft는 보존해야 한다.

### FR-009 버전 조회 및 diff
시스템은 두 확정 버전 또는 Draft와 최신 확정 버전을 비교할 수 있어야 한다.

**수용 기준**
- front matter/공통 메타데이터 변경과 본문 라인 단위 변경을 함께 표시한다.
- 추가, 삭제, 수정이 구분된 diff 결과를 제공한다.
- 비교할 원본 버전과 대상 버전을 명확히 표시한다.
- 버전 스냅샷은 DynamoDB에서 읽고 FastAPI가 diff를 계산한다.

### FR-010 DOCX 내보내기
시스템은 Markdown 기반 문서를 DOCX로 생성할 수 있어야 한다.

**수용 기준**
- 제품에 내장한 md-publisher 기반으로 Markdown, 표, 로컬/S3에서 해석 가능한 이미지 참조 및 YAML front matter 표지를 DOCX로 변환한다.
- 외부 패키지 서비스 또는 별도 실행 파일을 사용자가 준비하지 않아도 제품 기능으로 동작한다.

### FR-011 추적표 관리
시스템은 사용자스토리, 요구사항, 테스트케이스 사이의 추적 관계를 기록하고 Excel 추적표로 출력해야 한다.

**수용 기준**
- 하나의 사용자스토리는 여러 요구사항과 연결될 수 있고, 하나의 요구사항은 여러 테스트케이스와 연결될 수 있다.
- 누락된 연결 또는 유효하지 않은 참조를 식별할 수 있다.
- 추적표는 사용자스토리 ID, 요구사항 ID, 테스트케이스 ID 및 관계 상태를 포함한다.

### FR-012 Bedrock 요구사항정의서 AI 작업공간
시스템은 사용자가 **현재 선택한 프로젝트 안에서** 채팅형 AI 작업공간을 열고, RFP/제안요청서 텍스트와 후속 지시를 Amazon Bedrock에 대화식으로 전달해 요구사항정의서 내용을 생성·수정하게 해야 한다.

**수용 기준**
- AI 작업공간을 비롯한 산출물 메뉴는 사용자가 프로젝트를 만들거나 선택해 프로젝트 컨텍스트에 들어온 뒤에만 사용할 수 있다.
- MVP 입력은 텍스트/Markdown 붙여넣기이며, 관리자는 후속 메시지로 자료와 요구사항정의서 내용을 대화식으로 보완·수정할 수 있다.
- 각 AI 응답은 편집 가능한 요구사항정의서 미리보기/작업 결과를 갱신하되, 대화 중에는 문서나 버전을 정식 저장하지 않는다.
- 관리자는 작업 결과를 검토한 뒤에만 현재 프로젝트에 새 요구사항정의서 Draft 문서로 저장할 수 있다. 저장된 Draft는 일반 편집·버전 확정 흐름을 따른다.
- 요청 실패 또는 비정상 응답 시 현재 미저장 작업 결과와 기존 Draft를 훼손하지 않고 재시도 가능한 오류를 제공한다.

## 7. 비기능 요구사항
### NFR-001 사용성
React UI는 프로젝트, 문서, Draft, 버전 목록 및 diff 대상/결과를 명확히 구분해야 한다. 버전 확정은 확인 절차를 요구한다.

### NFR-002 데이터 무결성
DynamoDB 저장 모델은 문서별 단일 Draft와 확정 버전의 불변성을 보장해야 한다. 같은 문서의 동시 확정은 조건부 쓰기 또는 동등한 낙관적 동시성 제어로 중복/충돌을 방지해야 한다.

### NFR-003 저장 제약
DynamoDB 아이템의 400KB 제한을 고려해 이미지와 큰 바이너리는 S3로 분리한다. 대형 문서 본문이 제한을 초과할 가능성은 구현 설계에서 크기 정책 및 S3 오프로딩 여부를 결정한다.

### NFR-004 AI 생성 품질
Bedrock 생성 결과는 초안으로만 취급해야 하며, 사용자 검토·수정·확정 없이는 공식 문서 버전으로 저장하지 않아야 한다.

### NFR-005 유지보수성
산출물 유형, 렌더러(Markdown/DOCX/XLSX), 저장소, diff 계산은 분리 가능한 인터페이스로 구현해 PPT 등 향후 유형을 추가할 수 있어야 한다.

### NFR-006 테스트 전략 및 PBT
예제 기반 테스트와 속성 기반 테스트를 병행한다. PBT 부분 적용의 강제 규칙은 PBT-02, PBT-03, PBT-07, PBT-08, PBT-09이다.

**수용 기준**
- Python 백엔드의 PBT 프레임워크로 Hypothesis를 선택하고 프로젝트 의존성에 포함한다.
- Markdown/front matter 및 문서 모델 직렬화·역직렬화에는 생성 입력 기반 round-trip 테스트(PBT-02)를 작성한다.
- 버전 불변성, 단일 Draft 등 명시한 불변조건에는 생성 입력 기반 invariant 테스트(PBT-03)를 작성한다.
- 문서/버전/추적 관계용 PBT 생성기는 현실적인 식별자, 구조 및 제약을 가진 도메인 생성기여야 한다(PBT-07).
- PBT는 축소와 재현 가능한 seed 정보를 지원하고 CI에서 실행하도록 설계한다(PBT-08).

## 8. 제약, 가정 및 미결 사항
- 로컬 실행 환경은 EC2이며 AWS 권한은 이미 이용 가능하다고 가정한다.
- 인프라 상세 설계, 배포 방식 및 프로덕션 보안/복원력 기준은 현재 범위에서 제외한다.
- Security Baseline과 Resiliency Baseline은 사용자가 명시적으로 미적용을 선택했다.
- DOCX 기능은 md-publisher의 초기 구현을 제품 내부에 포함해 발전시킨다. 라이브러리 코드의 라이선스·배포 적합성 검토는 구현 전 수행한다.
- 대형 원본 Markdown/Excel 구조화 데이터의 DynamoDB 저장 한계와 다중 사용자 협업 정책은 Application Design 단계에서 구체화한다.
